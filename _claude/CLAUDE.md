## Project setup
- iOS / iPadOS app. Swift 6 language mode with strict concurrency, iOS {{IOS_DEPLOYMENT_TARGET}} deployment target, Xcode pinned by `.xcode-version`.
- The Xcode project is generated by XcodeGen from `project.yml` (`make generate`) and is **not committed**. Edit `project.yml`, never the generated project; Info.plist keys, versions and entitlements all live there (`docs/xcodegen-regen-defenses.md` explains why).
- Platform-neutral logic goes in local Swift packages under `Packages/` that import Foundation only, so `make test-core` (`swift test`) runs anywhere a Swift toolchain exists, including cloud sessions without Xcode.
- Dependencies come in through SPM, declared in `project.yml`. `Package.resolved` is the source of truth for resolved versions.
- Run `make help` for the day-to-day commands. CI runs the same targets.

## Build pipeline
- Every push runs `.github/workflows/build.yml` on the self-hosted Mac runner: the Xcode pin check and `make check` always, then (unless the change builds nothing) `make lint`, `make generate`, `make test-core` and `make test-app`. New source files are picked up automatically.
- A push that changes only docs, `.claude/`, workflows or `fastlane/` takes the fast path (`scripts/detect_no_build.sh`), and so does a commit whose parent has the same files, build number aside, and passed the full build (`scripts/ci_reuse_build.py`).
- The required status check is the job id `build`. Don't give the job a `name:`.
- There is deliberately no `pull_request` trigger: a fork PR would run untrusted code on the runner that holds the signing key.
- UI tests run nightly in their own scheme (`ui-tests.yml`), off the merge gate.
- `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` are pinned at the project base in `project.yml` so every target ships aligned. Never override them per target.

## Design-driven development
- All non-trivial logic is driven by a low-level design (LLD). The only exception is bug fixes.
- Pick work from `design/Documentation/docs/03 - Low Level Design/todo/`. After shipping, update the LLD's `Status:` line and `git mv` it to `done/`. Use `git mv`, never a copy: CI fails the build if the same numeric prefix is in both directories.
- An LLD stays in `todo/` while anything in it is still to do, including checks that need a device; its `Status:` line says what has landed and what hasn't.
- New LLDs take the next free number and follow `03 - Low Level Design/LLD-TEMPLATE.md`: a `**Status:**` line, then `**Source:**` and `**Scope:**`, then numbered sections ending in tests and risks.
- Section numbers are cited across docs (`LLD 004 §3.2`, `HLD §5.6`), so don't renumber an existing doc's sections; add to the end or use sub-sections.
- Record the owner's decisions where the design records them, with the date ("owner's decision, 2026-11-10").
- Folder map under `design/Documentation/docs/`:
  - `01 - Proposal/` — the HLD and proposals.
  - `02 - Architecture/` — architecture references and the changelog.
  - `03 - Low Level Design/` — `todo/`, `done/`, and `manual-tests/` (runbooks that get re-run; state tracked inline via `Status:`).
  - `04 - Review/` — audits and review artefacts.

## Testing
- Non-trivial domain and business logic gets a unit test that validates the behaviour.
- There are no snapshot tests. The owner checks UI changes by eye on a device, so a PR that changes the UI says what to look at.

## Branching
- `main` reflects what's on the App Store. It is the release-of-record, tagged on every release (`appstore-<version>`), and nothing is developed on it. Expect `pre-prod` to be far ahead of it.
- `pre-prod` is the integration branch, tested on the Simulator and TestFlight.
- Cut every feature, fix and docs branch from an up-to-date `pre-prod`, and open its PR against `pre-prod`. Never target `main` with a dev branch's PR, even when asked to "merge to main" as a shorthand: confirm first.
- The only branch that merges into `main` is `pre-prod` itself, through a `pre-prod` → `main` PR when the owner releases (`main-source-guard.yml` enforces it). Don't open that PR unless asked.
- Never commit or push directly to `main` or `pre-prod`: a ruleset rejects it. Anything that commits, like the TestFlight build-number bump, does it on a short-lived branch merged by PR.
- If `main` ever carries a commit `pre-prod` lacks, merge `main` back into `pre-prod` through a PR.

## TestFlight
- Use the `release-to-testflight` skill to ship a build, and `signing-certs` for certificate and profile problems.
- Deploy from the current branch (typically `pre-prod`). Never deploy from `main`.
- Build numbers may skip: the developer releases builds outside Claude's view, so gaps are expected.
